# EP0 进度探针（P0-1）

三次重连尝试都没命中，原因是每次都在猜主机卡在哪个控制请求上。这个探针把这个猜测
变成读数：把 EP0 状态机的每一次迁移压缩成一个 32 位值，放在内核静态区里，panic 之后
随日志一起读出来。

## 为什么不用打印

失败往往发生在 `printf` 本身就依赖的路径上（控制台背后就是这条 USB），打印会递归，
而且 panic 之后环里可能还有没发完的内容。所以只记录，不输出；由已有的日志通道在
合适时机把这个值带出去。

## 打包格式

```
31            24 23        16 15         8 7            0
+----------------+------------+------------+------------+
|  事件序号 mod 256 |  阶段      |  请求号    |  状态码    |
+----------------+------------+------------+------------+
```

* **状态码**（bit 0-7）：最近一次动作的返回值，0 表示成功
  * `0` 成功
  * `1` 超时
  * `2` 命令被控制器拒绝（`DEPCMD` 状态非零）
  * `3` 端点未就绪
  * `4` 容量不足
  * `5` 状态阶段顺序错误
  * `16+n` `DEPCMD` 返回的具体状态 n
* **请求号**（bit 8-15）：`bmRequestType`/`bRequest` 的摘要
  * `0` 非请求事件（复位、连接、`XferNotReady`）
  * `1` `GET_DESCRIPTOR`
  * `2` `SET_ADDRESS`
  * `3` `GET_CONFIGURATION`
  * `4` `SET_CONFIGURATION`
  * `5` `SET_LINE_CODING`
  * `6` `GET_LINE_CODING`
  * `7` `SET_CONTROL_LINE_STATE`
  * `8` `GET_STATUS` / `CLEAR_FEATURE`
  * `255` 其它
* **阶段**（bit 16-23）
  * `1` 收到 SETUP
  * `2` 数据阶段已提交
  * `3` 数据阶段完成
  * `4` 等待 `XferNotReady(status=2)`
  * `5` 状态阶段已提交
  * `6` 状态阶段完成
  * `7` 已重新武装 SETUP
  * `16` 总线复位
  * `17` 端点重建
* **事件序号**（bit 24-31）：每次迁移自增，用来判断是否发生了回绕

## 记录点

在 `bsd/dev/kebab_usb.c` 里，以下每一处都要记录：

| 位置 | 阶段值 |
| --- | --- |
| `ud_event()` 收到 `type==1`（复位） | 16 |
| `ud_ep0_rebuild()` 结束 | 17 |
| `ud_setup()` 解析出 `bRequest` | 1 |
| 数据阶段 `ud_start()` 之后 | 2 |
| 数据阶段的完成事件 | 3 |
| 收到 `XferNotReady(status=2)` | 4 |
| 状态阶段 `ud_start()` 之后 | 5 |
| 状态阶段的完成事件 | 6 |
| 状态阶段之后重新提交 SETUP TRB | 7 |

每个记录点同时写 `ud.ep0_progress` 和一个递增到 32 项的环形历史
`ud.ep0_history[32]`，这样能看到失败前的最后几步，而不只是最后一步。

## 带出去的方式

panic 报告发完之后，在 `kebab_usb_panic_spin()` 里：

1. 把 `ep0_progress` 和整个历史环格式化成十几行文本
2. 直接写进 bulk IN 缓冲发送（不走日志环，避免递归）
3. 前缀固定为 `KEBAB EP0 PROBE:`，方便主机侧抓取

正常启动时则在 `bsd_init` 之后、USB 起来时打印一次当前值，作为基线。

## 验收

* 编译通过
* 正常启动能看到基线输出
* panic 之后能看到最后 32 次迁移，且能读出失败请求是哪一个、卡在哪个阶段

有了这个，P0-2 的 EP0 重写才有依据：先看读数，再改代码。
