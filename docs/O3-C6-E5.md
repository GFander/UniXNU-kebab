## 1. 事件分发机制（Mu 源码审计）

调用图（行号取自 `Mu_Basecore/MdeModulePkg/Core/Dxe`）：

```text
CoreExitBootServices (DxeMain/DxeMain.c)
  790  CoreNotifySignalList (&gEfiEventBeforeExitBootServicesGuid)
  802  CoreTerminateMemoryMap (MapKey)
  807  (失败) CoreNotifySignalList (&gEventExitBootServicesFailedGuid)
  816  (成功) CoreNotifySignalList (&gEfiEventExitBootServicesGuid)

CoreNotifySignalList (Event/Event.c:246)
  - 持 gEventLock，遍历 gEventSignalQueue
  - CompareGuid(Event->EventGroup, EventGroup) 命中才 CoreNotifyEvent(Event)

CoreNotifyEvent (Event/Event.c:213)
  - InsertTailList (&gEventQueue[Event->NotifyTpl], &Event->NotifyLink)
  - gEventPending |= 1 << NotifyTpl          // 仅入队，不执行

CoreDispatchEventNotifies (Event/Event.c:153)
  - 取 gEventQueue[Priority] 头，RemoveEntryList
  - 211 行 Event->NotifyFunction (Event, Event->NotifyContext)   // 真正执行点
```

要点：

- `CoreNotifySignalList` 只把匹配事件组的 **已注册事件** 入队，顺序为
  `gEventSignalQueue` 的插入顺序（即 `CreateEventEx` 注册顺序）；
- 真正执行发生在 `CoreDispatchEventNotifies`，按 TPL 队列顺序；
- 因此“17 个 NOTIFY 候选”是**注册数**，不等于 17 次执行；只有 TPL 队列里被
  取出的才会执行。

### SKIP_ALL 的语义

同型号实验里的 `SKIP_ALL=1` 位于 `CoreDispatchEventNotifies` 的循环内，跳过的是
**所有 TPL 队列中的通知**（不按事件组过滤），因此它会同时压制非 EBS 事件组与
普通 Boot Services 定时器/通知。它能启动只说明“某个/某些通知是挂死点”，不能
定位到 RpmhDxe。本轮两个方案都严格限定 `EFI_EVENT_GROUP_EXIT_BOOT_SERVICES`。

## 2. RpmhDxe 回调的可靠识别（方案，不是 RVA 猜测）

识别在三处建立，全部在 DXE Core 侧，不碰闭源二进制：

1. **镜像登记**：`CoreLoadImageCommon` 成功后登记 `(ImageBase, ImageSize,
   ImageHandle)`；RpmhDxe 由 `Handle` 的 DevicePath 末段文件名判定，而不是地址。
2. **事件登记**：`CoreCreateEventEx` 中若 `EventGroup == EBS GUID`，登记
   `(Event, NotifyFunction, EventGroup)`。
3. **判定**：仅当 `EventGroup == 27ABF055-…`、`NotifyFunction` 落在
   **RpmhDxe 镜像区间内**、且该 `(Event, NotifyFunction)` 在登记表中时，才认为
   是目标回调。

判据失败（未登记、地址不在镜像内、事件组不符）时**不跳过**，保持原始行为。
不使用 PE RVA `0x149c` 作为运行时地址；RVA 仅用于文档对照。

## 3. 两个诊断开关（离线补丁设计）

```c
/* 默认 0：正式构建行为不变 */
#ifndef KEBAB_EBS_SKIP_RPMH_CALLBACK
#define KEBAB_EBS_SKIP_RPMH_CALLBACK 0
#endif
#ifndef KEBAB_EBS_SKIP_EBS_GROUP
#define KEBAB_EBS_SKIP_EBS_GROUP 0
#endif
```

`CoreDispatchEventNotifies` 中、`Event->NotifyFunction (...)` 之前：

```c
if (KebabEbsFilterShouldSkip (&Event->EventGroup,
        (UINT64)(UINTN)Event->NotifyFunction,
        (UINT64)(UINTN)Event)) {
    continue;   /* 只跳过这一个事件，其他事件照常 */
}
```

`KebabEbsFilterShouldSkip()` 的策略：

- 宏都关闭 → 恒 0；
- 方案 A → 仅 EBS 组 + 已登记 + NotifyFunction 在 RpmhDxe 镜像内；
- 方案 B → 仅 EBS 组（该组所有回调）；
- 任何非 EBS 组 → 恒 0。

方案互斥由编译期宏选择，默认两者皆 0。

## 5. 与 KebabEbsProbe 的衔接

现有记录器可直接记录：

- `E2`（EBS 通知开始）——`CoreNotifySignalList` 之前，global 入口；
- `E3`（目标回调即将执行）——分发器命中目标时，callback 入口（需先
  `kebab_ebs_bind_callback(notify, event)`）；
- `E4..E6`——`CoreUninstallProtocolInterface` 及释放路径，target 入口；
- `E7`（目标回调返回）——callback 入口；
- `E8`（EBS 成功返回）——DarwinBoot 在 EBS 之后的写点。

诊断性跳过时记 `E3` 然后直接 `E7`（status = SKIPPED），可与真实执行区分。
不需要扩大记录器结构；记录与显示都限定在预先分配的记录页，EBS 后不调用
`Print`/`Allocate*`/`Free*`。
