# kebab 移植：交接文档

写于 2026-10-28 晚。目标：在 OnePlus 8T（kebab，SM8250，16 KiB 页）上跑起 iOS 16.7.16 用户态（iPhone X 身份），当前焦点是让 Apple 的 APFS 真正可用。

---

## 一、设备怎么操作

### 硬件与启动链

```
OnePlus 8T (kebab, SM8250)
  ABL → Mu-Silicium UEFI (UniXNU) → DarwinBoot → XNU
```

启动镜像烧在 `boot_b`（活动槽是 b）。镜像布局：

```
[0x000000, 0x800000)   引导器/固件区（来自 signed.img）
[0x800000, ...)        64 MiB FAT32 ESP，内核在 EFI/UniXNU/ 下
引导参数在              EFI/UniXNU/UNIXNU.TOML
```

### 常用命令

```powershell
# 进 fastboot：长按电源 15 秒关机，然后音量下 + 电源
D:\TOOL\platform-tools\fastboot.exe devices
D:\TOOL\platform-tools\fastboot.exe flash boot_b <镜像>
D:\TOOL\platform-tools\fastboot.exe reboot
```

### 串口控制台

内核 USB 控制台起来后出现 CDC-ACM 设备（VID_1209），Windows 侧是 **COM7**（每次可能是别的编号，按 VID 查）。

```powershell
# 按 VID 找端口
Get-CimInstance Win32_PnPEntity | Where-Object { $_.DeviceID -like '*VID_1209*' }
```

**抓日志的坑（重要）**：

```
控制台在"内核 USB 驱动起来之后"才存在，之前的所有输出只在环形缓冲里
恐慌后控制台会被 panic 泵接管，普通命令可能被拒绝
所以：不要指望"刷完再抓"，要么先开抓取再触发重启，要么读内核环形缓冲
```

### 可用的控制台命令

```
IMEM?  SPMI?  PON?  TCS?  PSCI?  PSCINEG?  VRMON  SYNC  FASTBOOT  FASTBOOT2  REBOOT
FWLOG? all   ← 读内核环形缓冲（64 KiB，见下）
```

`FWLOG?` 原来读固件环形缓冲（物理地址 `0xf44c0000`）——**那块内存在本平台读出来是全 0xFFFFFFFF**，等于永远读不到东西。现在已改成读**内核自己的** 64 KiB 环形缓冲，由 `kebab_usb_log()` 挂钩填充，panic 状态下也能读（限制 32 KiB）。

### 打包脚本

```powershell
cd D:\LOS\HiOS
python pack-payload.py <基础payload> <内核或prelink的bin> <输出payload> <toml>
python pack-boot.py   <signed.img> <payload> <输出boot镜像>
```

注意：**scp 前先建目标目录**，并且每次检查 `$LASTEXITCODE`。我因为把输出丢进 `Out-Null` 且不检查返回值，白刷了两次旧镜像。


### 关键的四条经验（每条都是一次 panic 换来的）

**一、C++ vtable 填充必须关**

```
APPLE_KEXT_VTABLE_PADDING 在 macOS 目标是 1、iOS 是 0
我们的 IOService vtable 274 字 vs 供体 170 字 → 虚函数派发全错位
补丁 0159 强制为 0，0160 删掉 438 个 _RESERVED* 导出名
```

**二、32 MiB 引导映射同余**

```
内核用 32 MiB L2 块建初始映射，要求 (physBase ^ virtBase) & 0x1ffffff == 0
预链接块放在内核下方会破坏它 → 表现是完全静默的设备挂起（无输出、无复位）
必须把预链接块放在内核上方：slide -0x1effcdc8000
```

**三、KPI 伪 kext 的假 Mach 头**

```
com.apple.kpi.* 的 _PrelinkExecutableLoadAddr 是小偏移，在我们的布局里不落在头上
slidePrelinkedExecutable()+0x48 会 data abort（far=0x180）
补丁 0162 校验魔数后按无可执行体返回
```

**四、doLockUnlockMedia 在 iOS 上不存在**

```
供体 vtable 槽 171 是 doSynchronizeCache，不是 doLockUnlockMedia
（后者是 macOS 专有）
vendored 头已改；驱动里实现了 doSynchronizeCache 返回 kIOReturnUnsupported
```

### 当前阻塞

**所有预链接组件都启动失败**：

```
Kext com.apple.kec.corecrypto module start pointer is outside of kext range
  (start 0xfffffe000891092c - kext starts at 0xfffffe00080344xx)
Kext ... start failed (result 0xdc008007)
→ 依赖链断 → apfs 报 AppleImage4 not found → 没有 APFS
```

矛盾点：**文件里段表是包含 start 的**

```
corecrypto __TEXT_EXEC = 0xfffffe00088c8000 + 0x48b3c，上界 0xfffffe0008910b3c
start = 0xfffffe000891092c   ← 在里面，只差 0x210 字节
```

而内核说不包含 → 运行时内存里的头部和文件不一致。

**已经排除**：

```
不是内存被释放          ml_static_mfree 次数已经是 0（osdata_phys_free 补丁生效），
                        但 start failed 仍有 11 次
不是 emitter 的滑动错   供体与我们的 kmod start 相对 load 的偏移完全一致（0x81cd14）
不是头文件锚点问题       文件里逐段读出来都对
```

## 四、下一步（按优先级）

### 一、把运行时内存里的组件头 dump 出来

加一个调试命令（如 `KEXT? <地址>`），运行时打印：

```
magic / ncmds / sizeofcmds / 每个段的 vmaddr + vmsize
```

和文件里的值逐个比，看是"被改写"还是"从没写进去"、偏了多少。这是唯一能结束猜测的手段。

### 二、试上游的做法：显式加载 APFS

```c
OSKextLoadKextWithIdentifier("com.apple.filesystems.apfs")
```

在 `bsd_init` 里、用 boot-arg 门控。若它能成功，说明问题只在启动期依赖解析，不在 kext 本身。

### 三、若上面都不行

考虑把预链接处理成 **MH_FILESET** 形态（Apple 会给 fileset 单独的内存路径，不会释放 `__PRELINK_TEXT`），或者干脆把 IOStorageFamily 从源码编进内核。
